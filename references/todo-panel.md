# 任务清单（Todo）面板的状态与呈现

本章整理桌面 Agent 应用里任务清单（Todo / Plan）面板的数据语义、更新策略与呈现边界。依据来自 ZCode 桌面端的实现（`packages/shared/src/tool-plan-adapter.ts`、`packages/ui/src/TodoPanel.tsx`、`packages/ui/src/ToolCallBlocks/renderers/todo.tsx`、`packages/ui/src/v4/conversationStatusPanelModel.ts`），属于参考实现而非强制模板。字段命名、状态取值与布局需按项目实际协议适配。

---

## 1. 最小数据模型

一条清单项只需要三个字段就能支撑完整呈现与后续扩展：

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| `content` | 非空字符串 | 一项工作的一句话描述，动词开头，可独立读懂 |
| `status` | `pending` / `in_progress` / `completed` | 只有三态。不要引入 `failed`、`blocked`、`cancelled` 到清单项上 |
| `priority` | `high` / `medium` / `low` | 协议层保留，界面不必默认暴露（见第 7 节） |

三态之外的信息（失败、被跳过、等待授权）属于**任务生命周期**，应落在会话状态与工具调用状态上，不要塞进清单项。清单项回答"还有哪些事要做"，会话状态回答"这一轮现在怎么样"，两者混用会让面板同时表达两套语义。

> [!NOTE]
> 需要支持多轮迭代时，可在清单外层加一个分组（ZCode 用 `{ id, source: "session" | "goal_iteration", goalIteration?, targetId?, startedAt?, updatedAt?, todos }`）。分组只是归属标记，不改变项本身的三态语义。

---

## 2. 快照语义：全量替换，不做增量合并

Todo 工具的输出是**当前完整清单的快照**，不是"变更集"。写入端每次提交整个数组，读取端整体替换。

这一条决定了后续所有呈现规则：

- 不要对两次快照做 diff 后合并（`completed` 项在下次快照里消失就是消失了，不是"被删除事件"）；
- 不要假设项的 `id` 稳定；ZCode 的适配层在缺 `id` 时直接回退用标题当 `id`；
- 不要缓存上一版清单再拼增量，否则停止、重试、子任务回退时会残留幽灵项。

---

## 3. 输入适配：宽容解析，但拒绝部分成功

Agent 侧工具名和字段名不总是规范，读取端适合做一层归一化（ZCode 的做法可直接借鉴）：

| 适配点 | 处理方式 |
| --- | --- |
| 工具名识别 | 匹配 `todo_read` / `todo_write` / `update_plan` 一类命名，允许 `_`、`-`、空格分隔 |
| 清单容器键 | 依次尝试 `todos`、`plan`、`steps`、`items` |
| 状态归一化 | 小写、`-` 转 `_`，只接受三态，其余视为无效 |
| 标题字段 | 依次尝试 `content`、`step`、`title`、`text`、`activeForm` |
| 纯字符串数组 | 容忍，首项视为 `in_progress`，其余 `pending` |

关键约束：**要么全部解析成功，要么整体丢弃**。ZCode 在校验时要求解析出的条目数等于原数组长度，否则返回 `null` 保持上一版。这条看似严格，实际是防御半截数据——如果 5 项里有 1 项标题为空就渲染 4 项，用户看到的是"任务凭空少了一个"，比不更新更糟。

---

## 4. 归属隔离：不要在父会话摘要里混入子任务清单

子代理（subagent）和 workflow 会把子工具调用镜像进父会话。如果这些内层 Todo 直接写进主清单，父任务的顶部摘要会被子任务的清单覆盖。

判断依据（ZCode `isMainAgentToolProjectionSource`）：出现 `source === "subagent"`，或存在 `parentToolCallId` / `parentToolUseId` / `_meta.claudeCode.parentToolUseId` 时，视为子级投影，不得覆盖主任务摘要。子级清单应显示在对应父工具调用块内部。

---

## 5. 顺序稳定性：不按状态重排

清单顺序由写入端决定，呈现端**保持原序**。

ZCode 在构建展示模型时留了明确注释：按状态重新分组会让已完成项从原位置跳到列表末尾，破坏快照的权威顺序（`conversationStatusPanelModel.ts` → `displayItems: plan.items`）。

用户是靠位置记住"我在第几步"的。一旦完成项下沉，每次状态变化整块列表都会跳动。若确实需要聚焦当前项，用折叠、筛选或滚动定位，不要重排数据。

---

## 6. 呈现分三层，各层职责不同

| 层级 | 位置 | 显示什么 | 不显示什么 |
| --- | --- | --- | --- |
| **摘要** | 会话顶部状态区 / 面板折叠态 | 当前项标题 + `已完成/总数` | 完整列表、优先级 |
| **面板** | 展开的 Todo 面板 | 未完成项列表 | 已完成项（折叠时不展示） |
| **内嵌** | 对应工具调用块内部 | 该次调用的完整快照（含已完成） | 与其他任务的混合 |

计数用等宽字体（`font-mono`），避免数字变化时宽度跳动。

折叠态的当前项选择顺序：`in_progress` → 第一个非 `completed` → 最后一项。三级兜底保证任何残缺快照都有可读标题。

---

## 7. 视觉状态与"不要谎报在跑"

三态的基础表达：

| 状态 | 指示器 | 文本 |
| --- | --- | --- |
| `pending` | 空心圆，最弱前景色 | 次级文字色 |
| `in_progress` | 实心/箭头标记，主前景色 | 主文字色 |
| `completed` | 勾选，成功色 | 最弱色 + 删除线 |

两条容易被忽略的边界，ZCode 都是踩过之后修出来的：

1. **全完成即隐藏面板**。上游可能先把所有项标成 `completed`，稍后才推任务结束事件清空状态。这段间隙如果继续显示"已完成清单"，用户会以为还有事没做完。全完成时直接隐藏。
2. **运行期动画只在真正运行时出现**。任务已结束、失败或被停止时，快照里可能仍残留 `in_progress` 项。此时若继续套用渐变文字或旋转图标，面板会永远显示加载态。非运行期降级为纯文本 + 静态状态色。

同理，工具调用块内部的 `in_progress` 用静态箭头而不是 spinner——工具输出里的 running 状态可能长时间挂在页面上，旋转图标会和真正的加载语义混淆。

## 8. 交互与可访问性

- **点击区域不要铺满容器**。ZCode 的教训是：撑满布局的 header 如果整体可点击，留白区域也会误触。展开逻辑收敛到"内容宽度按钮 + 右侧图标按钮"两个明确目标。
- 两个入口都要带 `aria-expanded`，图标按钮补 `aria-label` 与 `sr-only` 文本，键盘可达（`focus-visible` 环）。
- 折叠态标题 `truncate`，计数 `shrink-0`，长标题不能挤压计数。
- 展开/收起状态属于局部 UI 状态，不要写进会话持久化数据。

---

## 9. 常见缺陷对照

| 现象 | 常见根因 |
| --- | --- |
| 任务完成后列表整体跳位 | 呈现端按状态重排 |
| 面板一直显示加载中 | 非运行期仍套用运行态动画 |
| 完成后面板还在，显示一堆删除线 | 未做全完成隐藏；展开态未过滤已完成项 |
| 任务数量突然变少 | 部分解析成功被当成整体成功 |
| 主任务摘要变成子任务标题 | 未做子代理投影隔离 |
| 停止后残留 "进行中" 且无法消除 | 缓存了增量状态而非整块快照 |
| 计数位置抖动 | 计数未用等宽字体或未固定宽度 |

---

## 10. 验收要点

- [ ] 五种快照场景都能正确呈现：首项 `in_progress`、全 `pending`、部分完成、全完成、单字符串数组；
- [ ] 提交一个含空标题项的清单，界面保持上一版而非渲染残缺列表；
- [ ] 任务被停止后，面板不再出现任何运行态动画；
- [ ] 全部完成后面板消失，而不是变成一条条删除线；
- [ ] 从折叠态切到展开态再切回，滚动位置与当前项标题不跳变；
- [ ] 键盘 Tab 可达折叠按钮，`aria-expanded` 随状态变化；
- [ ] 子代理产生 Todo 时，父任务摘要不受影响。

> [!IMPORTANT]
> 本节只覆盖清单本身的呈现。清单状态是否真实，取决于上游是否按真实执行事件写入快照；界面层无法修正被伪造的进度。相关约束见 [任务状态与控制权](agent-interaction.md)。
